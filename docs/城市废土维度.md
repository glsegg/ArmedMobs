# 城市废土维度（`tarkovscav:urban_wasteland`）— 实测记录

> 本文件记录**跑出来的数字**，不是设计意图。每一条都给出取证方式：专用服务器（`tools/spike/citysave/server`，Forge 1.20.1-47.4.3）上的 RCON 输出、区域文件（`.mca`）直读扫描、或对 `build/libs/armedmobs-0.1.0-all.jar` 的反汇编。
> 测试用世界：`UrbanWasteland`（新目录，种子 20240913），未触碰任何已有世界。

## 1. 怎么进去

| 方式 | 谁 | 说明 |
| --- | --- | --- |
| `tarkovscav:deployment_beacon`（部署信标） | 生存玩家，主路径 | 主世界右键 → 40 tick（2 秒）读条 → 进入废土；在废土内右键 → 回到上次出发的主世界坐标（`data/tarkovscav_retreat.dat`，按 UUID）。受伤 / 移动超过 4 格 / 提前松手 / 换维度 / 掉线都会中断并给出提示。冷却 10 秒，物品不消耗 |
| `/armedmobs dimension [<name>]` | 管理员（权限 2） | 默认传送到废土，带名字则传送到该维度。与信标**共用同一套落地代码**（`world/WastelandTravel.java`） |

落地保护：目标列取玩家自己的 X/Z，Y 由 `MOTION_BLOCKING` 高度图决定并向上找到两个不碰撞的格子；落点下方没有可站立地面时铺 5×5 石砖平台并在角落放火把。

## 2. 地形（由 `tools/make_wasteland_dimension.js` 从原版 `overworld.json` 派生）

| 项 | 取值 | 理由 |
| --- | --- | --- |
| `offset` 噪声缩放 | **0.35** | 只压地形起伏，不动 y 梯度：城区能坐得住，山丘保留约 1/3 |
| `sea_level` | **-63**（基岩底为 -64） | 海平面以下才注水，于是**没有海洋、湖泊、洞穴水** |
| 地表调色 | coarse_dirt / gravel / andesite 覆盖 tuff / stone | 死城色，无草 |
| 矿脉 | 关闭（`ore_veins_enabled=false`，三个 vein 字段为常数 0） | 死城不要铜铁矿脉 |
| 含水层 | **关**（`aquifers_enabled=false` + `default_fluid=minecraft:air`） | 用户反馈「连接中间有可以掉下去的水」；关掉含水层后**新生成**区块的缝隙里不再有水。**已生成**区块里的水用 `/armedmobs fillwater` 清（数据包改不了旧区块） |

**实测（512×512 方块采样，262,144 列）**：

* 地表 Y：最小 19、最大 148、平均 **113.6**
* 水方块列数：**0（0.00%）** → “无水”已被证明
* 地表方块直方图（前几名）：coarse_dirt 39.9%、gravel 12.7%、andesite 7.0%、cobblestone 3.4%，其余为城区建材
* 地表归属：**只属于城区建材调色板的占 57.90%**，与废土调色板共用的占 39.28%，只属于废土的占 2.82%，其它 0.00%
  （“共用”指 stone/andesite/gravel/coarse_dirt/cobblestone —— 地形与地基都会用，因此**不**算作人造，这是保守口径）

## 3. 密度：一个自定义放置类型，两张网格

1.20.1 **数据包维度不能覆盖 structure_set**：`javap` 的 `net.minecraft.world.level.dimension.LevelStem` 显示数据包用的 codec 只读 `type` 与 `generator`，`DimensionStructuresSettings` 只在原版三维度的 level.dat 路径上使用。写进维度 JSON 的 `structures` 块会被静默丢弃 —— 实测：写进去时同一 512×512 采样区只有 **2** 个城区结构（正是主世界稀疏间距）。

因此密度由 `tarkovscav:wasteland_spread`（`worldgen/WastelandSpreadPlacement.java` + `worldgen/ModWorldgen.java`）提供：`isStructureChunk` 判断该 chunk 生成器的 `BiomeSource` 是否为持有 `tarkovscav:urban_wasteland` 的 `FixedBiomeSource`，是则用 dense 网格，否则用原版网格；两条分支都是**同一段原版随机散布算式**（含带 salt 的 `setLargeFeatureWithSalt`）。

**主世界不变**：同一颗种子、同一 512×512 采样区，自定义放置的构建与“四个结构集改回 `minecraft:random_spread`”的对照构建，`tarkovscav:` 结构起点**逐区块完全一致**（`city_a @ chunk 5,3`、`city_small @ chunk 1,0`）。

**建筑刷率 -75%（用户要求）**：四个结构集统一 `"frequency": 0.25`。`javap` 的 `StructurePlacement#isPlacementChunk` 证明判定顺序是「生物群系 → `if (frequency < 1.0F) shouldGenerate(seed, salt, x, z, frequency)` → 排斥区 → `isStructureChunk`」，所以这一个值同时作用于主世界与废土，且保持网格 / salt / separation 不变（改 `spacing` 会移动网格，故未采用）。只影响**新生成**区块。

| 结构集 | 主世界网格（chunks） | 废土 dense（chunks） | 占地（方块） |
| --- | --- | --- | --- |
| `city_small` | 24 / 8 | **24 / 8**（原 4 / 1） | 48 |
| `city_variants` (a/b/c) | 32 / 12 | **24 / 8**（原 5 / 2） | 40..64 |
| `city_district` | 48 / 20 | 16 / 5（**故意不动**：这个就是「大城市」拼装器） | 自组装 ≤256 |
| `city_strongpoint` | 192 / 48 | 192 / 48（**故意保持稀疏**） | 138×66 |

**2026-10 收尾：废土间距从 4~5 格区块改成 24 格区块（= 384 格一座城）。** 原因有两层：一是预制体本身
宽 48~64 格，而 5 格区块 = 80 格、4 格区块 = 64 格，也就是**城市网格比城市还窄**，两座城必然互相压边
（压边的结果就是缝隙、连接残留和显眼的水），二是密度本身就意味着区块生成代价。`city_district`
（16 格）与 `city_strongpoint`（192 格）**没动**：前者是用户点名要的「大城市」、靠密铺街道块连成片，
后者是十八栋楼的稀有据点。

**实测结构数（`structures.starts` 直读区域文件，非启发式）**：

| 采样区 | 构建 | 城区结构数 |
| --- | --- | --- |
| 废土 512×512 | 最初误以为生效的维度内覆盖（等于主世界稀疏间距） | **2** |
| 废土 512×512 | 自定义放置 + dense 6/8/32 + frequency 1.0 | **46**（small 26 / a 11 / b 2 / c 5 / district 2） |
| 废土 512×512 | **最终**：自定义放置 + dense 4/5/16 + frequency 0.25 | **119**（small 67 / a 18 / b 18 / c 12 / district 4） |
| 主世界 512×512 | 对照（`minecraft:random_spread`，frequency 1.0） | 2 |
| 主世界 512×512 | **最终**（frequency 0.25） | 2 |
| 主世界 1024×1024 | 对照（frequency 1.0） | 12 |
| 主世界 1024×1024 | **最终**（frequency 0.25） | **0** |

**改间距之后的期望（算术，未实测）**：把 `city_small` 与 `city_variants` 的 dense 网格从 4/1 和 5/2
换成 24/8 之后，同样的 512×512 采样区里这两套的候选点从「每 5 格区块一个」降到「每 24 格区块一个」，
即候选点数按面积比约为原来的 1/23 与 1/27（`city_district` 的 16 格没动，所以原 4 个 district 大致不变）。
旧的 **119** 是改之前实测的，**不能**拿来当现在的数字：要看真实结果必须在游戏里重新采样区域文件
（`tools/spike/work/citymap/WastelandScan.java` 那一套），我没有重跑，这里只给算术。

算术与诚实说明：`frequency` 把每个候选点的接受概率乘 0.25，期望正好 25%。两个主世界样本合起来是 **2/14**（基线 14/14），即观测 14% —— 与 25% 在小样本下的涨落一致（泊松均值 3.5 时 P(≤2)≈32%），但样本太小，**不能**用这两个数去钉死比例；机制本身由反汇编证明，样本只是佐证。

地图：`docs/maps/urban_wasteland.png`（1204×1303，2 px/方块，含图例与网格，地面 Y=111，最高建筑高出 37 格），另有 `_height_1px.png`（692×813）与 `_floors.png`（2448×3509，分层切片）。

## 4. 建筑与室内（2026-09-25 的两个生成器后处理）

用户报的两个缺陷都是**结构 NBT 里的显式方块状态**问题：游戏放置结构时**不会**重跑 `updateShape`，所以生成器必须自己把连接状态烘进去。

| 结构 | 连接方块总数 | 修复前“该连却没连” | 修复后 |
| --- | --- | --- | --- |
| `city_strongpoint.nbt` | 8,510 → 8,254 | 8,250 | **0** |
| `city_small.nbt` | 1,742 → 1,698 | 1,742 | **0** |
| `city_a.nbt` | 1,718 → 1,705 | 1,718 | **0** |
| `city_b.nbt` | 2,095 → 2,064 | — | **0** |
| `city_c.nbt` | 1,424 → 1,366 | — | **0** |
| `gen_district.nbt` | 1,012 → 976 | 1,012 | **0** |
| `structures/buildings/*`（用户手工几何） | — | 0 | 0（未改动） |

* `bakeConnectorStates()`：按原版规则重算每个 `*_pane` / `iron_bars` / `*_fence` / `*_wall` —— 玻璃板/栅栏连“同族或完整支撑面”，墙的四面为 `tall`（邻墙）/`low`（完整面）/`none`，`up` 按直连规则（直线上不立柱、端点/转角/十字立柱并向上传递）。结构外邻居视为不可连（与原版结构一致）。
* `repairDoorways()`：恢复每扇门的两半，并清掉门轴两侧各两格（含头顶），保证 2 格通行；**内部分隔墙上的无门门洞也被记录并同样保护** —— 它们以前对后处理不可见，而最后运行的掩体线生成可以把一个掩体块塞进房间唯一的门洞里，把房间封死。
* `ensureConnectivity()`：从每栋入口洪泛，凡是到不了的房间就在它墙边开一个 2 格洞（“留着封死”是唯一不被允许的结果）。生成器输出 `sealedRooms / breached`，六个结构最终都是 `sealedRooms=0`。

**关于两个“独立检查器报出的残留”（已定案）**

第二轮复核用 `tools/spike/work/citymap/verify_strict.js` 报出连接方块残留 13/5/6/16/63/9、门被挡 4/1/3/5/18/2。两个数字都被复现了，但两个都是**检查器谓词的假阳性**，不是结构缺陷：

1. **连接方块那组是“把空气当成可连接”**。该工具自己的输出就写着 `triggered by: south->minecraft:air`；我直接读 NBT 探针也确认 `11,3,10` 的邻居是「北=stone_brick_wall，其余=air」。原版（javap 反汇编）`FenceBlock.connectsTo = isSameFence || 栅栏门 || isSideSturdy(FULL)`、`IronBarsBlock.connectTo = 同类 || isFaceSturdy(FULL)`、`WallBlock` 只对「邻墙」给 `tall`、对「完整面」给 `low` —— **空气和异族连接体都不连**，所以那些“孤立栅栏腿”在游戏里本来就该没有臂。
   正面证据（`node tools/spike/out/door_and_fence_proof.js`）：city_small 现有 **3,472** 条臂（同族 2,230 + 完整面 1,242）、city_a 3,580、city_b 4,242、city_c 2,817、据点 17,654、gen_district 2,062，而**该连却没连 = 0**（六个结构全部）。也就是说朝 `polished_andesite` 这类完整面的臂确实写进去了。
2. **门那组是“门楣”**。用同一个 3D 打印器看被点名的门（city_small 9,3,16）：门那一行是 `stone pane stone chise >>DOOR chise DOOR chise stone`，门自身两个高度（y=2、y=3）内侧 z=15 全是 `.`（空气），而 **y=4 是墙** —— 那是门楣，任何嵌在墙里的门上面都有一层墙。该检查器同时遍历门的上半块并要求它上方也是空气，所以只有“立在空地上的门”才能通过。我的闸门把门楣单独计数并打印，六个结构恰好是 **4/1/3/5/18/2** —— 与它的门计数完全相同，一一对应。

据此，`tools/selftest_blockstates.js` 已按**移动真实可通行**加严（门洞只认空气/水/熔岩，`*_wall`/`*_fence`/`*_pane`/`*_bars` 一律算堵），并额外断言“臂数 > 0”（防止把一个空烘培也判为通过），同时把「只有空气当邻居的侧面数」打印出来作为对照。加严后六个结构：门洞被堵 **0**，连接缺失 **0**，墙缺面 **0**。

用户自己的 `structures/buildings/building_b1.nbt` 有 9 处门洞侧面被挡（5 扇门）；闸门对 `buildings/*` 只打印不断言，**不改动他的手工作品**。

**四个预设 + 据点 + gen_district 已按原 layout / 原种子重新生成**，因此字节必然变化：`tools/selftest_strongpoint.js` 里的 sha256 钉子已更新（旁边写明这是**有意的**重生成），`tools/selftest_blockstates.js` 是新的“必须为 0”闸门。用户存档里**已经生成**的城区保持旧几何（worldgen 只影响未生成区块）。

## 5. 已证明 / 未核对

**已证明（有取证）**

* 专用服务器加载干净：`Registry loading errors` / `Failed to parse` / `Failed to load datapacks` 全无；`Done (18.013s)!`；维度真实存在（`ThreadedAnvilChunkStorage (urban_wasteland): All chunks are saved`）
* 维度/群系/噪声/特征/标签 JSON 全部可加载，且由 `tools/selftest_datapack.js`（390 条事实）按真实 codec 区间钉死
* `locate biome tarkovscav:urban_wasteland`、`locate structure city_strongpoint / city_small / city_district` 都返回真实坐标
* forceload 1168 区块、`setblock`、`fill`、`time query` 都有正常回包
* 密度：废土 512×512 = 119 个城区结构（基线 2）；主世界两个样本 frequency 1.0 → 0.25 的计数如上表
* 连接状态 0 未连、墙的四面显式、门洞 2 格通行（六个结构）
* 四个预设的 sha256 钉子在重生成后更新，且 `workspace-unchanged` 闸门证明生成器可复现（同一 layout 再跑字节相同）
* `tools/spike/selftest.ps1` 最后一行 `all self-tests passed`

**未核对（需要真人/客户端）**

* 信标的右键读条、粒子、落地平台、返程 —— 无头服务器上没有玩家实体，控制台来源只会走“非玩家”拒绝分支
* 废土在真实客户端里的观感（雾色/天光、建筑与地形接缝、119 个结构同屏的性能）
* 138 宽的据点在 dense == normal == 192 chunks 下的稀疏度是否符合手感
* 长时间自然刷怪（群系 spawners 的权重只是 `monster` 类别内的相对份额，不是速率）
* 已有存档里旧城区的门/墙连接状态（worldgen 不会回填）
* `buildings/building_b1.nbt`（用户手工建筑）有 2 处门洞侧面被挡 —— 闸门只打印不断言，未改动他的几何
